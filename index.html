Team 8 · Capstone · ML System Design & LLMOps

LLM CostGuard

A layer in front of a support bot’s LLM. It reuses safe answers, sends only the policy text that matters and picks the cheaper model when it is safe. Each answer costs less and stays correct.

AaryaAryanHarshPrathmeshPurvanshSarthak

Hi, we are Team 8. Our project is LLM CostGuard, menu project 12. It sits in front of a customer-support LLM and makes each answer cheaper without making it wrong. Every number we show comes from the repo’s results or today’s live run; targets and estimates are labelled.

01 · Problem framing

A support bot pays full price for every answer

Big prompts

7,800

tokens in a large request: the customer’s case plus 8 attached policies. 34 of 40 held-out questions need only one of them.

Repeated questions

11 / 40

held-out questions repeat an earlier one: 5 word for word, 6 reworded. Each one is paid for again.

One model for all

20×

Sonnet 5.5 costs 20× Haiku 5.5 per token ($2 / $10 vs $0.10 / $0.50 per 1M in / out). Easy questions still go to the big model.

Business objective

Cut the LLM cost of each support answer to ≤ 35% of a full-context Sonnet 5.5 baseline, while keeping wrong answers ≤ 2.5%.

Our setting is Northstar Market, a fictional store with 23 policies. Every support request sends Claude the customer’s message, their case and a bundle of policies. Money leaks three ways: big prompts of about 7,800 tokens, repeated questions, and one expensive model for everything. Our objective in one sentence: cut the cost of each answer to at most 35% of a full-context Sonnet baseline, while keeping wrong answers at or below 2.5%.

The system takes a request and returns a grounded answer plus its cost. Inside, there are three prediction problems. Cache reuse: does one correct answer serve both questions? We score it by wrong hits on 49 traps, look-alike questions that need a different answer. Context selection: which sections keep every gold fact, meaning the facts a correct answer must state, inside an 800-token budget. And the router: what is the probability that this query needs the large model? We score it by complex queries sent to the small model, and that must be zero. The scope is bounded. The domain is Northstar Market, a fictional store with 23 policy documents and single-turn English questions. In scope: the two caches, the window, the router, shadow evaluation, monitoring and CI gates, with each tenant's cache kept apart. Out, on purpose: retrieval, because the caller attaches the policies, multi-turn chat, live compression, fine-tuning, and production hardening like auth and rate limits.

This is the whole system. A client calls one endpoint, POST /v1/answer. The request runs from the cheapest step to the most expensive. One: the exact cache in Redis; a hit is free. Two: the semantic cache. We embed the query, find the five nearest cached questions, and run three free checks; only survivors reach a one-word Haiku judge. On a miss, three: the window trims the policies to 800 tokens. Four: the router picks Sonnet or Haiku. Then one Claude call, and the answer is stored in both caches. Solid lines are synchronous. Dashed lines run in the background: the shadow baseline in parallel, Prometheus scraping metrics, and Langfuse receiving traces.

04 · LLMOps · deployment and tools

Serving, rollout, rollback, and the tools behind them

Serve

  • FastAPI on uvicorn: POST /v1/answer, /metrics, /healthz; starts in 2.2 s
  • Claude is a managed API; bge-small and the router run in-process on CPU
  • Docker Compose: Redis Stack, Prometheus, Grafana; Langfuse as a 6-container profile

Next: app container image, 2+ workers behind a load balancer, HNSW index

Roll out

  • Every cache key holds config_version: a new prompt or model starts a clean cache
  • CI gates every pull request: caches, window, held-out quality and cost
  • Shadow mode compares new vs baseline on the same live request

Canary plan: one tenant goes to a second process on the new config, shadow on; promote if the CI quality bounds hold, else route back

Roll back

  • git revert → the old config_version returns → its cache entries (under 7 days old) serve again: a warm rollback
  • DELETE /api/cache?tenant= purges one tenant’s cache
  • Old namespaces clean themselves up: every cache key has a 7-day TTL

Verify: replay mode re-runs a fixed trace through the service for $0 and confirms the old numbers

Three constraints shaped every choice. A budget of 5 to 20 dollars, so we memoize every call; the whole project spent 5.30. A model call takes about 4.4 seconds, so cheap checks run first, and a miss adds only 24 milliseconds. And only 190 team-written queries, so we split by topic and keep the router cautious. Now four trade-offs. We chose free checks plus a Haiku judge over cosine alone, because traps score as high as paraphrases: wrong answers fell from 43 to 1 on 49 traps. We chose a context window over LLMLingua-2, because compression saved only 3 percent more, kept every fact in only half the queries, and cannot cut output, about half of a miss’s cost. We chose 800 tokens over 1,200, because 1,200 costs 24 percent more for one more correct answer in 40. We chose bge-small over MiniLM, because it serves 31 versus 20 of 36 paraphrases. Then the failure modes. A changed number, a flipped negation and a different customer case each went to zero wrong hits. An edited policy or prompt changes the key, so an old answer cannot match. The tenant is in every key and every vector search. And the router leans to Sonnet: on held-out, none of the 29 misses went to Haiku.

Backup · Q&A prep 1 / 2

Likely questions, with short honest answers

Isn’t the full-context baseline a straw man?

Partly. 29 of 40 requests attach 8 policies and 34 need one. A retrieval baseline would shrink the window’s savings, not the cache’s 27.3 points.

Why not Haiku 5.5 for everything?

≈ $0.0007 per query at config prices (estimate), a fifth of ours, but never graded. 15 of 40 held-out queries need the large model. Our strongest open question.

Is the learned router better than simple rules?

Not yet: −14.5% cost with 8.5% complex leaks, vs rules −10.4% with 3.2%. It needs more labels or a per-category gate.

Were the CI bounds set after seeing the results?

Yes. They are regression gates that lock in the measured level. The proof of quality is the held-out eval, not the gate.

Sonnet answers, grades and judges. Is that biased?

Possibly; we have no human agreement figure yet. The bias touches both arms: all 29 held-out misses also used Sonnet. Next: two people grade blind (Cohen’s kappa).

Backup · Q&A prep 2 / 2

Likely questions, with short honest answers

What breaks first at 10× traffic?

Not the caches: the shared 8-thread pool with shadow on, ≈ 1.8 shadowed requests/s per process (estimate). Fix: sample shadow, async calls, more workers; later HNSW instead of a FLAT index.

Why is the cache judge Haiku 4.5, at 10× Haiku 5.5’s price?

Not compared yet. Judge spend is 0.9% of held-out cost, so accuracy matters more than price. Testing Haiku 5.5 is next.

How is a bad cached answer removed?

Today: the 7-day TTL or a tenant purge. Reuse is limited to the same docs and case. Plan: evict on a shadow “worse” verdict.

What was the most consequential design decision?

Making cache reuse depend on the request context (cached docs + case ⊆ request). Alone it cut wrong hits 43 → 21, and it shaped the key, invalidation and tenant isolation.

Where do 50 ms and 300 req/s come from?

Our budgets: 50 ms ≈ 1% of a 4.4 s model call; 300 req/s so one process is not the bottleneck before the model API. Measured: 31.7 ms and 332 req/s, model mocked, shadow off.
